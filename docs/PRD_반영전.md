# 학생자치 재정 예방 플랫폼 PRD

Nov 7, 2026 · @coordit

## 1. 개요

곳간지기(가칭)는 학생회 재정을 **학기 전에는 세칙 체크리스트로 준비시키고, 학기 중에는 영수증을 모아 두고, 감사 기간에는 통장 거래내역과 자동으로 맞춰 수입지출 내역서를 만든 뒤, 감사 세칙과 과거 감사 기록을 근거로 LLM이 현행 서류를 판단해 감사 초안을 쓰게 하는** 서비스다. 감사위원회가 확정한 결과는 일반 학생에게 학과별 점수와 감점 사유로 공개된다.

### 두 개의 화면 영역

| 영역 | 사용자 | 하는 일 |
| --- | --- | --- |
| 관리자(admin) | 학과 학생회 회계 담당·학생회장, 감사위원회 | 체크리스트, 영수증·통장 업로드, 내역서 생성, 감사 판단 실행·검토·확정 |
| 학생 공개 페이지 | 일반 학생 | 학과별 감사 점수, 등급, 감점 사유와 근거 조항, 시정 여부, 학기별 추이 |

### 핵심 기능 3가지 + 공개

| # | 기능 | 언제 | 입력 | 출력 |
| --- | --- | --- | --- | --- |
| 1 | 영수증 수집과 수입지출 내역서 자동 생성 | 학기 중 수집, 감사 기간 생성 | 영수증 사진(수시), 통장 거래내역 엑셀 | 영수증 메타데이터, 영수증↔출금 대사 결과, 지정 양식 내역서 |
| 2 | LLM 감사 판단 | 감사 기간 | 감사 세칙 원문, 현행 서류(사업계획서·회의록·결과보고서 등), 내역서·대사 결과, 체크리스트 이행 기록, 과거 감사 기억 | 조항별 판정과 근거 인용, 감점, 점수 초안, 확인 질문 |
| 3 | 학기 일정 기반 세칙 체크리스트 | 학기 시작 전 | 학기 일정(과잠 공동구매, 축제, MT 등) | 행사별 준비 자료·기한, 감사위원회 사전 고지 사항(별도 통장 개설 등) |
| 공개 | 학생 공개 페이지 | 감사 확정 후 | 확정된 감사 결과 | 학과별 점수·감점 사유 페이지 |

LLM은 두 곳에서 쓰이며 **서로 분리된다.** 체크리스트를 만드는 LLM(기능 3)과 감사를 판단하는 LLM(기능 2)은 모델·프롬프트·입력이 다르고 서로의 출력을 기준으로 삼지 않는다(5.4절).

### 한 줄 요약

미리 알려주고(체크리스트), 미리 모아 두고(영수증), 감사는 LLM이 세칙과 선례로 초안을 쓰고 사람이 확정하며, 결과는 학생에게 공개한다.

### 배경과 문제

- **영수증과 통장 맞추기:** 결산 때 영수증 더미와 통장 내역을 한 줄씩 맞추고 양식에 옮겨 적는다. 영수증을 잃어버리거나 칸이 밀리는 실수가 여기서 생긴다.
- **감사 인력 부족:** 감사위원 몇 명이 여러 학과의 서류를 세칙과 하나하나 대조한다. 지난 학기에 비슷한 사례를 어떻게 판단했는지는 기억에 의존한다.
- **사전 고지 누락:** 학생 돈을 걷는 사업은 별도 통장 개설과 감사위원회 고지가 먼저 필요한데, 사업이 끝난 뒤에야 알게 된다.
- **결과가 학생에게 닿지 않음:** 감사 결과를 찾기 어렵고 이유를 알기 어렵다.

**현장 근거 (발표 전 확보):**

- [ ] 최근 감사의 지적 유형별 건수와 점수 분포 (감사위원회 기록, 건수만 집계하고 조직명은 비공개)
- [ ] 증빙 누락·사전 고지 누락 지적 건수
- [ ] 회계 담당의 결산 소요 시간, 감사위원 1명이 학과 하나를 보는 데 걸리는 시간

### MVP 범위

| 항목 | MVP에서 다루는 범위 |
| --- | --- |
| 학과 | 시연용 가상 학과 3개, 실제 세칙은 1개 학과 기준 |
| 영수증·통장 | 가상 영수증 30\~50장(로컬 OCR), 1개 은행 거래내역 양식 |
| 내역서 양식 | 해당 학과의 수입지출 내역서 양식 1개 |
| 감사 대상 서류 | 사업계획서, 회의록, 결과보고서 3종 (가상) |
| 기억 | 가상 과거 감사 기록 2개 학기 분량 |
| 범위 밖 | 은행 계좌 직접 연동, 예산 예측, 세칙 정합성 검증, 학교 시스템 연동, 실제 학생 데이터 공개 |

### 목표

1. **영수증을 미리 모으게:** 사진 한 장이면 일시·가맹점·금액·품목이 저장되고, 감사 기간에는 통장과 자동으로 맞춰진다.
2. **내역서 자동 생성:** 대사 결과로 지정 양식의 수입지출 내역서를 만들고, 증빙 누락을 알려준다.
3. **LLM 감사 판단:** 감사 세칙 원문과 과거 감사 기억을 함께 주고 현행 서류를 조항별로 판단하게 한다. 판정마다 서류의 근거 문장과 조항을 인용하게 하고, 코드가 인용을 검증한다. 점수는 코드가 감점 기준표로 계산하고, 확정은 감사위원이 한다.
4. **사전 체크리스트:** 학기 일정만 넣으면 별도의 LLM이 세칙에서 행사별 준비 자료·사전 고지 사항을 뽑고, 코드가 기한을 계산한다.
5. **학생 공개:** 확정된 결과를 학과별 점수와 감점 사유로 보여준다.

### 성공 지표 (목표치, 평가용 데이터로 1회 측정)

| 지표 | 목표 | 측정 방식 |
| --- | --- | --- |
| 영수증 인식 | 금액 98%, 일시 95%, 가맹점 90% 이상 정확 | 평가용 영수증 필드별 정답 비교 |
| 대사 자동 확정 정확도·비율 | 정확도 98% 이상, 비율 80% 이상 | 평가용 정답 쌍 |
| 내역서 변환 | 셀 단위 일치율 99% 이상 | 정답 내역서와 셀별 비교 |
| 감사 판정 일치 | 조항별 판정이 감사위원 판정과 85% 이상 일치 | 평가용 결산 사례 10건 |
| 인용 정확도 | LLM이 인용한 근거 문장이 실제 서류에 있는 비율 100% (없으면 자동으로 확인 필요) | 코드 검증 |
| 점수 일치 | 감사위원이 매긴 점수와 ±5점 이내, 10건 중 8건 이상 | 평가용 사례 |
| 판정 안정성 | 같은 입력 2회 호출 시 조항별 판정 일치 95% 이상 | 반복 호출 |
| 체크리스트 | 정답 준비 목록 대비 재현율 95% 이상, 기한 오차 0 | 가상 학기 일정 3개 |
| 공개 페이지 이해도 | 학생 5명 중 4명이 “우리 과가 왜 감점됐는지 알겠다” | 시연 후 설문 |

가중치·임계값·프롬프트는 조정용 데이터에서만 정하고, 평가용 데이터는 개발이 끝난 뒤 한 번만 돌린다(10절).

## 2. 사용자와 시나리오

### 페르소나

| 사용자 | 상황 | 필요한 것 | 쓰는 화면 |
| --- | --- | --- | --- |
| 과 학생회 회계 담당 | 영수증 관리와 결산을 혼자 맡는다 | 영수증을 잃어버리지 않고, 결산 때 손으로 맞추지 않기 | 관리자: 영수증, 대사·내역서, 체크리스트 |
| 과 학생회장 | 학기 사업을 정한다 | 사업마다 지킬 절차를 미리 알기 | 관리자: 체크리스트 |
| 감사위원 | 인력은 적고 학과는 많다 | 서류를 세칙과 대조한 초안과 비슷한 선례를 받아 판단에만 집중 | 관리자: 감사 판단·검토·확정 |
| 일반 학생 | 학생회비를 냈다 | 우리 과가 돈을 잘 썼는지, 감점됐다면 왜인지 | 학생 공개 페이지 |

### 사용자 스토리

- 회계 담당으로서, 결제할 때마다 영수증을 찍어 올리면 내용이 저장되길 원한다.
- 회계 담당으로서, 감사 기간에 통장 거래내역 엑셀만 올리면 영수증과 맞춰져 학과 양식 내역서가 나오길 원한다.
- 학생회장으로서, 학기 일정을 넣으면 사업마다 준비할 자료와 감사위원회에 미리 알릴 일을 알고 싶다.
- 감사위원으로서, 서류마다 어느 조항을 충족했는지·못 했는지가 근거 문장과 함께 정리된 초안을 보고, 고쳐서 확정하고 싶다.
- 일반 학생으로서, 우리 과와 다른 과의 감사 점수와 감점 사유를 쉽게 보고 싶다.

### 대표 시나리오: 한 학기의 처음과 끝

1. **학기 전 (기능 3):** 학생회장이 “3월 과잠 공동구매(수금 120명), 4월 MT, 5월 축제 부스”를 입력한다. 체크리스트 LLM이 세칙에서 해당 의무를 뽑고, 코드가 기한을 계산해 “별도 통장 개설 후 감사위원회 고지 D-14, 수요조사, 견적 2곳 비교, 정산 결과 공개 D+14”를 근거 조항과 함께 보여준다.
2. **학기 중 (기능 1):** 회계 담당이 결제할 때마다 영수증을 찍어 올린다. OCR이 일시·가맹점·금액·품목을 읽고, 불확실한 칸만 고친다. 체크리스트 항목은 완료할 때마다 체크하고 자료를 첨부한다.
3. **감사 기간 (기능 1):** 통장 거래내역 엑셀을 올린다. 헝가리안 알고리즘이 영수증과 출금을 맞추고, 영수증 없는 출금 2건을 “증빙 누락”으로 표시한다. 확인을 마치면 학과 양식 내역서가 만들어진다.
4. **감사 (기능 2):** 감사위원이 감사 판단을 실행한다. 시스템이 행사별로 감사 패킷(관련 세칙 조항, 그 행사의 서류·내역서·증빙 누락, 체크리스트 이행 기록, 이 학과의 지난 감사와 비슷한 선례)을 만들어 감사 LLM에 보낸다. LLM은 조항마다 충족·미충족·확인 필요를 근거 문장과 함께 돌려준다.
5. 코드가 인용을 검증하고 점수를 계산한다: **86점(한정)**. 감점 사유는 증빙 누락 2건(−6, 반복 지적 가중), 과잠 정산 결과 미공개(−8)다. 축제 부스 결과보고서의 “행사 목적 부합”은 LLM 두 번의 판정이 엇갈려 확인 질문으로 남는다.
6. 감사위원이 질문에 답하고 감점 하나를 조정한 뒤 확정한다. 확정 결과는 기억에 저장되고, 학생회가 소명·시정을 입력할 수 있다.
7. **공개:** 일반 학생이 공개 페이지에서 학과별 점수를 보고, 우리 과를 눌러 감점 사유·근거 조항·시정 여부를 확인한다.

### 사용자 흐름

&#91;관리자\] 세칙·감점 기준표 등록 → 학기 일정 → 체크리스트 이행 → 영수증 수시 업로드 → (감사 기간) 통장 업로드 → 대사 확인 → 내역서 → 감사 판단 실행 → 초안 검토·확정 → 공개 승인 \[학생\] 공개 페이지 → 학과 목록(점수·등급) → 학과 상세(감점 사유·근거·시정 여부·학기별 추이)

## 3. 기능 요구사항

P0가 시연의 전부다. P1은 시간이 남을 때만 만들고, P2는 발표 마지막 로드맵 한 장에만 올린다.

| ID | 기능 | 설명 | 핵심 기술 | 우선 |
| --- | --- | --- | --- | --- |
| F0 | 세칙·감점 기준표 등록 | 세칙 원문을 조·항·호로 나누고, 감사위원회가 감사 대상 조항과 조항별 심각도·감점, 등급 구간을 입력한다 | 조항 파싱, 설정 화면 | P0 |
| F1-a | 영수증 업로드·OCR | 사진을 올리면 일시·가맹점·금액·품목(세목)을 읽어 메타데이터로 저장. 행사 태그 | 로컬 OCR + 자기 검산 | P0 |
| F1-b | 통장 거래내역 읽기·가명처리 | 1개 은행 양식 엑셀을 표준 거래로 바꾸고 이름·계좌를 코드화 | 은행 양식 파서, HMAC + 암호화 매핑표 | P0 |
| F1-c | 영수증↔출금 대사 | 전체 최적 매칭, 애매하면 확인 필요, 나눠·묶음 결제는 부분집합 합 | 헝가리안 + 점수 차 확인 + 부분집합 합 | P0 |
| F1-d | 수입지출 내역서 생성 | 품목 기반 계정과목 분류 후 지정 양식 셀에 값 입력, 잔액·합계 검산 | 규칙 분류 + TemplateSpec + openpyxl | P0 |
| F2-a | 감사 패킷 구성 | 행사별로 관련 조항 원문, 서류 텍스트(가명), 내역서 행, 증빙 누락, 체크리스트 이행 기록, 기억에서 고른 선례를 묶는다 | 코드 (조항·행사 매핑, 선례 검색) | P0 |
| F2-b | 감사 판단 LLM 호출 | 패킷을 감사 LLM에 보내 조항별 판정·근거 인용·심각도·확인 질문을 JSON으로 받는다. 행사별 1회 + 학과 전체 1회, 각 2회 호출 | LLM API, 구조화 출력 | P0 |
| F2-c | 판정 검증·점수 계산 | 인용 문장·조항 실존 확인, 숫자 주장은 내역서와 대조, 2회 판정 불일치는 확인 필요. 감점 기준표로 점수·등급 계산 | 코드 | P0 |
| F2-d | 기억 (memory) | 확정된 과거 감사, 감사위원 판단 사유, 학과별 반복 지적 저장·검색 | DB + 조항 id 일치 + 텍스트 유사도 | P0 |
| F2-e | 초안 검토·확정 | 감사위원이 판정·감점을 수정하고 확정, 공개 승인. 확정 결과는 기억에 저장 | 화면, 이력 | P0 |
| F3 | 학기 일정 체크리스트 | 체크리스트 LLM이 세칙에서 행사별 의무를 뽑고, 코드가 조항 실존 확인·기한 역산·선후 정렬. 이행 체크·첨부 | 별도 LLM + 위상 정렬 | P0 |
| F4 | 학생 공개 페이지 | 학과별 점수·등급, 감점 사유·근거 조항·시정 여부, 학기별 추이 | 공개 승인된 결과만 | P0 |
| F5 | 소명·시정 입력 | 학생회가 감점 사유에 소명·시정 결과를 달고 공개 페이지에 함께 표시 | 상태 관리 | P1 |
| F6 | 감사 결과서 PDF, 체크리스트 ICS | 문서·캘린더 내보내기 | HTML → PDF, ICS | P1 |
| F7 | 예산 예측, 세칙 정합성 검증, 중앙 관제, 인수인계 | 확장 | 몬테카를로, Z3, 집계 | P2 |

범위 밖: 은행 계좌 직접 연동, 실제 결제·송금, 학교 시스템(HY-in) 연동, 감사위원회의 최종 판단 대체.

## 5. 알고리즘과 로직

숫자로 판단할 수 있는 것(대사, 증빙 누락, 잔액, 기한, 점수)은 코드가 하고, 서류를 세칙에 비추어 읽는 일은 LLM 호출이 한다. LLM 호출은 정해진 순서로 한 번씩 이뤄지며 스스로 다음 행동을 고르지 않는다(에이전트 방식이 아님). 토큰은 더 쓰지만 구조가 단순하고 결과를 추적하기 쉽다.

### 5.1 기능 1: 영수증 수집과 수입지출 내역서

**① 영수증 인식 (학기 중).** 서버 안의 로컬 OCR로 일시, 가맹점명, 사업자번호, 금액, 품목(세목)을 뽑고 자기 검산한다(품목 합 = 합계, 공급가액 + 부가세 = 합계, 날짜·사업자번호 형식). 검산이 맞지 않거나 신뢰도가 낮은 칸은 노란색으로 표시하고 올린 사람이 고친다.

**② 통장 거래내역 읽기 (감사 기간).** 은행 양식 파서로 읽고 적요의 이름·계좌번호를 바로 코드로 바꾼다.

**③ 영수증↔출금 대사.** 영수증 m장과 출금 n건을 짝짓되 짝 전체의 비용 합이 가장 작게 한다.

`s(i,j) = w_a·S_amt + w_d·S_date + w_m·S_name` (시작값 w\_a 0.5, w\_d 0.2, w\_m 0.3, 조정용 세트로만 조정)

짝지은 비용은 `c(i,j) = 1 − s(i,j)`. 행렬을 (m+n)×(m+n)으로 늘리고 미매칭 비용을 한쪽당 `δ = (1 − s_min) / 2 = 0.3`(s\_min = 0.4), 더미끼리는 0으로 두면 **s > 0.4일 때만 짝을 짓는다.** 날짜 차이 7일 초과나 금액 차이 50% 초과는 큰 비용으로 막고, scipy `linear_sum_assignment`로 푼다. s ≥ 0.85이고 2위 후보와 점수 차 ≥ 0.1이며 이 쌍을 금지했을 때 총비용이 Δ 이상 늘 때만 자동 확정하고, 아니면 이유와 함께 “확인 필요”로 보낸다. 남은 미매칭 중 합이 맞는 조합(1:N, N:1)은 부분집합 합으로 찾아 항상 확인 필요로 보낸다. 결과는 자동 확정, 확인 필요, **증빙 누락**(영수증 없는 출금), **통장에 없는 영수증**이다.

**④ 내역서 생성.** 영수증 품목과 가맹점 업종으로 계정과목을 분류하고(키워드 사전), 잔액 연속성과 총계를 검산한 뒤, 양식별 TemplateSpec에 따라 정해진 셀에 값을 넣는다. 서식과 수식은 유지한다.

### 5.2 기능 2: LLM 감사 판단

감사위원이 실행 버튼을 누르면 아래 다섯 단계가 순서대로 한 번씩 돈다.

**① 감사 패킷 구성 (코드).** 행사마다 하나씩, 그리고 학과 전체(결산·사전 고지 등 행사에 묶이지 않는 조항)용으로 하나 만든다.

| 패킷 구성 요소 | 내용 |
| --- | --- |
| 세칙 조항 | 감사 대상 조항 중 이 행사에 해당하는 것의 **원문 전체** |
| 현행 서류 | 이 행사의 사업계획서·회의록·결과보고서 텍스트 (가명처리) |
| 숫자 사실 | 내역서의 이 행사 행, 총액, 증빙 누락 목록 (기능 1 결과, 코드가 계산) |
| 이행 기록 | 체크리스트 의무별 완료 여부·첨부 (기능 3 결과, 사실로만 전달) |
| 기억 | 이 학과의 지난 감사 감점 사유, 같은 조항의 과거 선례 상위 3건(학과·학기·판정·감사위원 판단 사유) |

**② 감사 LLM 호출.** 패킷을 넣고, 조항마다 아래 형식으로만 답하게 한다(구조화 출력, temperature 0). 같은 패킷을 **두 번** 호출한다.

```json
{
  "clause": "제15조 제3항",
  "verdict": "미충족",
  "evidence": [{"doc": "결과보고서-과잠", "quote": "정산 내역은 추후 공지 예정"}],
  "reason": "수금 사업의 정산 결과를 공개해야 하나 공개 기록이 없음",
  "severity": "중대",
  "precedents": ["2025-2-기계공학과-F3"],
  "question": null
}
```

프롬프트에는 다음을 고정한다: 판단 기준은 주어진 세칙 원문뿐이다. 근거는 반드시 서류 문장을 그대로 인용한다. 서류에 없으면 “확인 필요”로 답한다. 선례는 참고일 뿐 기준이 아니다. 숫자 사실은 주어진 값을 그대로 쓴다. 점수는 매기지 않는다.

**③ 판정 검증 (코드).**

- 인용한 문장이 실제 서류에 있는지 문자열로 확인한다. 없으면 그 판정은 “확인 필요”로 바꾼다.
- 조항 id가 감사 대상 조항에 있는지 확인한다.
- 금액·날짜·건수 주장은 내역서·대사 결과와 대조한다. 숫자 판정(증빙 누락 건수, 한도 초과)은 LLM 답과 상관없이 코드 결과를 쓴다.
- 두 번의 호출에서 판정이 다르면 “확인 필요”로 바꾸고 두 답을 모두 보여준다.

**④ 점수 계산 (코드).** 미충족 판정에 감점 기준표의 조항별 감점을 적용하고, 기억에 같은 조항의 직전 학기 감점이 있으면 반복 가중을 곱한다. “확인 필요”는 감점하지 않은 점수와 감점한 점수를 함께 보여준다(점수 범위).

| 항목 | 값 (예시, 감사위원회 기준으로 교체) |
| --- | --- |
| 시작 점수 | 100 |
| 감점 | 경미 −1\~2, 중요 −3\~5, 중대 −8\~10 (조항별 지정) |
| 반복 지적 가중 | 직전 감사와 같은 조항이면 ×1.5 |
| 등급 | 90 이상 적정, 75\~89 한정, 75 미만 부적정 |
| 의견거절 | 통장 거래내역·내역서 등 필수 자료가 없으면 점수를 내지 않음 |

**⑤ 검토·확정·기억 저장.** 감사위원이 판정과 감점을 수정·확정하면 수정 내역과 판단 사유가 AuditCase로 기억에 저장되어 다음 감사의 선례가 된다. 감사위원이 자주 뒤집는 조항은 프롬프트·조항 해석 점검 대상으로 표시한다.

**토큰 예산:** 패킷 하나는 조항 원문 2\~5천, 서류 3\~10천, 선례·숫자 사실 2천 토큰 정도다. 학기 행사 10개 + 학과 전체 1개를 2회씩 호출하면 학과당 약 30만\~40만 입력 토큰이다. 비용은 들지만 호출 수가 정해져 있어 예측할 수 있다.

### 5.3 기능 3: 학기 일정 기반 세칙 체크리스트

1. **의무 추출 (체크리스트 LLM):** 학기 일정의 행사마다 세칙 원문을 넣고, 해야 할 일·근거 조항·기한 규칙(D-14 등)·선행 항목을 JSON으로 받는다. 같은 행사 유형(예: 수금 사업)은 한 번 감사위원이 검수한 결과를 저장해 다음 학기에 재사용한다.
2. **검증 (코드):** 근거 조항이 실제로 있는지, 인용한 조항 문장이 원문에 있는지 확인한다. 없으면 그 항목은 “검수 필요”로 표시한다.
3. **기한 계산 (코드):** 선행 관계(수요조사 → 견적 비교 → 사업계획서 승인 → 별도 통장 개설 → 감사위원회 고지 → 수금 시작)를 방향 그래프로 만들어 위상 정렬하고, 행사일에서 거꾸로 기한을 계산한다. `기한(의무) = min(규칙의 기한, 후속 의무의 기한 − 후속 의무의 소요일)`. 순환이 있으면 감사위원에게 알린다.
4. **경고:** 기한이 지난 항목은 “이미 늦음”, 한 주에 4건 이상 몰리면 “몰림”으로 표시한다.

| 행사 조건 (예시) | 준비 자료·할 일 | 기한 |
| --- | --- | --- |
| 학생에게 돈을 걷는 사업 (과잠 공동구매 등) | 별도 통장 개설, 감사위원회 사전 고지, 수요조사, 환불 기준 공지, 정산 결과 공개 | D-14 \~ D+14 |
| 예상 금액이 기준 이상인 행사 | 사업계획서 작성·승인, 견적 2곳 이상 비교 | D-7 |
| 외부 업체와 계약 (MT 숙소, 축제 장비) | 견적서, 계약서 사본 | D-7 |
| 모든 행사 | 결과보고서, 회의록 | D+7 |

### 5.4 두 LLM의 분리

|  | 체크리스트 LLM (기능 3) | 감사 LLM (기능 2) |
| --- | --- | --- |
| 하는 일 | 세칙에서 해야 할 일을 **미리 뽑는다** | 제출된 서류가 세칙을 **지켰는지 판단한다** |
| 입력 | 세칙 원문 + 학기 일정 | 세칙 원문 + 현행 서류 + 숫자 사실 + 이행 기록 + 기억 |
| 기억 접근 | 없음 | 과거 감사·선례 |
| 모델·프롬프트 | 별도 모델(또는 별도 제공사)과 별도 프롬프트 | 별도 모델과 별도 프롬프트 |
| 서로의 출력 | 감사 결과를 보지 않음 | 체크리스트를 **기준으로 쓰지 않고** 이행 사실로만 받음. 기준은 언제나 세칙 원문 |

분리하는 이유: 같은 AI가 기준을 만들고 채점까지 하면 세칙을 잘못 읽은 부분이 양쪽에서 똑같이 반복되어 걸러지지 않는다. 둘을 나누면 서로 다른 읽기가 교차 검증이 된다. 체크리스트에 없던 의무를 감사 LLM이 미충족으로 판단하거나 그 반대라면, 그 조항은 세칙 해석이 갈리는 곳이므로 감사위원에게 따로 알려 규칙을 다듬는다.

### 5.5 학생 공개 페이지

- 감사위원회가 **공개 승인**한 결과(PublishedResult)만 나간다. 초안·LLM 원문 답·확인 질문은 공개하지 않는다.
- 감점 사유는 공개용 문장으로 바꿔 쓴다. 개인 이름·계좌·영수증 이미지는 없고, 금액은 감사위원회가 정한 공개 범위(예: 행사 단위 합계)만 보인다.
- 학과 목록(점수·등급·지난 학기 대비 변화), 학과 상세(감점 사유·근거 조항·감점·시정 여부·학생회 소명), 학기별 추이를 보여준다. 목록은 기본으로 학과 이름순으로 정렬해 순위 경쟁보다 사유를 앞에 둔다.

## 6. AI 사용 원칙과 개인정보

### AI를 쓰는 곳과 쓰지 않는 곳

| 작업 | 담당 | 이유 |
| --- | --- | --- |
| 영수증 글자 읽기 | 로컬 OCR + 자기 검산 | 원본 이미지를 외부로 보내지 않는다 |
| 영수증↔출금 대사, 내역서, 증빙 누락, 기한 계산, 점수 | 코드 (헝가리안, 부분집합 합, TemplateSpec, 위상 정렬, 감점 기준표) | 숫자 판단은 같은 입력에 같은 결과여야 한다 |
| 세칙 → 행사별 의무 | 체크리스트 LLM | 문장 해석이 필요하다. 코드가 조항 실존을 검증한다 |
| 현행 서류의 세칙 충족 판단 | 감사 LLM (2회 호출) | 서류 문장을 세칙에 비추어 읽는 일이다. 코드가 인용·숫자·일관성을 검증한다 |
| 최종 판정·점수 확정·공개 | 사람 (감사위원회) | AI는 초안까지만 쓴다 |

### LLM 사용 안전장치

- LLM은 정해진 순서로 한 번씩 호출되며, 도구를 고르거나 데이터를 바꾸지 않는다.
- 판단 기준은 세칙 원문뿐이다. 선례는 참고, 체크리스트는 이행 사실로만 들어간다.
- 모든 판정에는 서류 인용과 조항이 붙고, 인용이 실제 서류에 없으면 자동으로 확인 필요가 된다.
- 숫자 판정과 점수는 코드가 낸다. LLM이 쓴 숫자는 점수에 쓰지 않는다.
- 두 번 호출해 판정이 엇갈리면 사람에게 넘긴다.
- 모든 패킷과 LLM 원문 답을 저장해 감사위원이 언제든 다시 볼 수 있다.

### 개인정보 처리 순서

실제 서비스로 운영할 때의 순서다. 해커톤에서는 가상 데이터만 쓴다.

1. **저장:** 영수증 원본, 통장 파일, 서류 원본은 서버에만 암호화해 저장한다.
2. **영수증:** 서버 안의 로컬 OCR로 읽는다. 원본 이미지는 외부로 보내지 않고, 카드번호는 끝 4자리만 남긴다.
3. **통장·서류:** 서버 안에서 읽고, 이름·계좌번호·전화번호를 바로 코드(HMAC)로 바꾼다.
4. **외부 LLM:** 가명처리한 텍스트만 보낸다. 두 LLM 모두 같다.
5. **재식별:** 코드↔실명 대응은 별도의 암호화된 매핑표(CodeMap)에 두고, 키는 감사위원회가 보관한다. 감사위원만 사유를 입력하고 열람하며 기록이 남는다.
6. **공개:** 공개 페이지에는 개인정보가 없다. 공개 승인 전에 감사위원이 공개용 문장을 확인한다.
7. **파기:** 보존 기간이 끝나면 원본과 매핑표를 함께 지운다.

**해커톤 예외:** 로컬 OCR 품질이 부족하면 가상 영수증에 한해 외부 비전 모델을 쓸 수 있고, 발표에서 이를 밝힌다.

### 법적·운영 검토 사항

실제 운영 전에 학교 개인정보 담당 부서와 총학생회·감사위원회 규정을 확인한다. 특히 학과별 감사 점수 공개 범위와 방식, 외부 LLM으로 보내는 서류 범위(가명처리 후), 보존 기간, 열람 권한을 문서로 정한다.

## 7. 시스템 아키텍처와 기술 스택

세칙 원문은 두 LLM이 각자 따로 읽는다. 체크리스트 LLM은 학기 전에 할 일을 뽑고, 감사 LLM은 감사 기간에 현행 서류를 판단한다. 영수증·통장 대사(기능 1)는 LLM 없이 알고리즘으로 돈다. 대사 결과와 체크리스트 이행 기록은 숫자 사실로만 감사 패킷에 들어가고, 감사위원이 확정한 결과는 공개 페이지와 기억으로 간다.

| 30h | P0 완성. 조정용 세트에서 탐욕 vs 헝가리안 비교, 감사 LLM 2회 판정 일치율 확인, 프롬프트 고정 |
| 36h | 평가용 세트를 한 번 돌려 OCR·대사·판정 일치·인용 정확도·점수 일치 측정 |
| 40h | 기능 동결. 이후에는 버그 수정과 발표 자료만 |
| 48h | 리허설 2회, LLM 응답을 미리 저장해 둔 재생 모드와 녹화 영상 준비 |

## 10. 검증과 리스크

### 검증 방법

가중치·임계값·프롬프트는 조정용 데이터에서만 정하고, 발표 수치는 평가용 데이터를 한 번 돌린 결과만 쓴다.

| 측정 | 방법 | 목표 |
| --- | --- | --- |
| OCR 필드 정확도 | 금액·일시·가맹점·품목별 정답 비교 | 금액 98%, 일시 95%, 가맹점 90% |
| 대사 자동 확정 정확도·비율 | 자동 확정 쌍의 정답 비율, 전체 중 자동 확정 비율 | 98% 이상, 80% 이상 |
| 내역서 | 정답 내역서와 셀별 비교 | 99% 이상 |
| 조항별 판정 일치 | 감사위원이 매긴 조항별 판정과 비교 (확인 필요는 별도 집계) | 85% 이상 |
| 인용 정확도 | 인용 문장이 실제 서류에 있는 비율 (코드 검증) | 검증 후 100% |
| 판정 안정성 | 같은 패킷 2회 호출 시 판정 일치 | 95% 이상 |
| 점수 일치 | 감사위원이 매긴 점수와 비교 | 10건 중 8건 ±5점 이내 |
| 체크리스트 | 정답 준비 목록 대비 재현율, 기한 오차 | 95% 이상, 0일 |

**경계 테스트:** 대사 점수 0.39/0.41, 같은 날 같은 금액 2건, 1:N·N:1·환불, 영수증 0장, 검산이 틀린 영수증, 서류가 없는 행사(→ 확인 필요 또는 의견거절), 인용이 서류에 없는 LLM 답, LLM이 숫자를 틀리게 말한 경우(코드 값 우선), 2회 판정 불일치, 등급 경계 점수(89/90), 반복 지적 가중, JSON 형식이 깨진 응답(재시도 1회 후 확인 필요), 체크리스트 순환·지난 기한.

### 비교 기준

| 비교 | 보여 주는 것 |
| --- | --- |
| 탐욕 매칭 vs 헝가리안 | 비슷한 후보가 많을 때 전체 최적의 차이 |
| LLM에 모든 자료를 통째로 넣기 vs 감사 패킷 + 검증 | 판정 일치, 인용 정확도, 숫자 오류, 2회 일관성 |
| 선례 없음 vs 선례 포함 | 조항별 판정 일치율과 학과 간 감점 일관성 |
| 같은 LLM으로 체크리스트·감사 vs 분리 | 세칙 해석 오류가 양쪽에 같이 나타나는지 |

### 리스크

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| 감점 기준이 명문화돼 있지 않음 | 점수의 근거가 약해짐 | 해커톤 전 감사위원들과 기준값을 정하고, “기준은 감사위원회가 설정”이라고 밝힘 |
| LLM 판정 오류·환각 | 잘못된 감점 | 인용 검증, 숫자는 코드 값 우선, 2회 불일치는 확인 필요, 최종 확정은 사람 |
| 토큰 비용·지연 | 실행이 느리고 비쌈 | 호출 수가 정해져 있어 미리 계산 가능. 행사별 병렬 호출, 결과 캐시 |
| 점수 공개에 대한 학생회 반발 | 도입 거부 | 공개 승인 절차, 소명·시정 표시, 순위가 아닌 사유 중심 화면. 공개 범위는 규정으로 정함 |
| 시연 중 API 실패 | 발표 중단 | 저장해 둔 LLM 응답 재생 모드 + 녹화 영상 |
| 로컬 OCR 품질 부족 | 업로드 단계가 느려짐 | 초반 2시간 비교, 자기 검산 + 직접 수정, 가상 영수증에 한해 외부 비전 모델 |
| 범위 확장 유혹 | P0 미완성 | 예산 예측·Z3·중앙 관제는 로드맵 한 장으로만, 40h 기능 동결 |

### 7분 구성

| 시간 | 장면 | 전할 내용 |
| --- | --- | --- |
| 0:00 | 학생 공개 페이지 | “우리 과 학생회비, 잘 쓰였을까?” 점수와 감점 사유로 시작해, 이 결과가 어떻게 만들어지는지로 넘어간다 |
| 0:45 | 현장 숫자 | 지적 유형별 건수, 회계 담당·감사위원의 소요 시간 |
| 1:30 | 기능 3: 학기 전 | 일정을 넣자 과잠 공동구매에 “별도 통장 개설 + 감사위원회 고지 D-14”가 근거 조항과 함께 뜬다 |
| 2:30 | 기능 1: 학기 중·감사 기간 | 영수증 사진 한 장 → 메타데이터. 통장 엑셀 → 헝가리안 대사 → 증빙 누락 2건 → 내역서 엑셀 |

| 5:00 | 다시 공개 페이지 | 방금 확정한 결과가 학생 화면에 뜨는 것을 보여준다 |
| 5:30 | 신뢰 | 판정 일치율, 인용 검증, 숫자는 코드가 계산, 두 LLM 분리, 개인정보 흐름 |
| 6:30 | 로드맵 한 장 | 중앙 관제, 예산 예측, 세칙 정합성 검증, 다른 학과·단과대 확장 |

### 예상 질문

| 질문 | 답 |
| --- | --- |
| LLM이 틀리게 판단하면? | 판정마다 서류 문장과 조항을 인용하게 하고, 인용이 실제 서류에 없으면 자동으로 확인 필요가 된다. 두 번 호출해 엇갈리면 사람에게 넘긴다. 최종 확정은 감사위원이 한다 |
| 점수도 LLM이 매기나? | 아니다. LLM은 조항별 충족 여부만 판단하고, 점수는 감사위원회 감점 기준표로 코드가 계산한다 |
| 왜 LLM을 두 개로 나눴나? | 같은 AI가 기준을 만들고 채점하면 같은 오해가 양쪽에 반복된다. 나누면 서로 교차 검증이 되고, 둘이 다르게 읽은 조항은 해석이 갈리는 곳이라 감사위원에게 알린다 |
| 토큰 비용은? | 학과 하나에 입력 30만\~40만 토큰 정도이고 호출 수가 정해져 있어 미리 계산할 수 있다. 행사 유형별 결과는 캐시한다 |
| 개인정보는? | 영수증은 서버 안에서 로컬 OCR로 읽고, 외부 LLM에는 가명처리 텍스트만 간다. 실명 확인은 감사위원만 열람 기록과 함께 한다 |
| 점수 공개는 학생회에 부담 아닌가? | 감사위원회가 승인한 것만 공개하고 소명·시정을 함께 보여준다. 학기 전 체크리스트로 감점 자체를 줄이는 것이 목표다 |
